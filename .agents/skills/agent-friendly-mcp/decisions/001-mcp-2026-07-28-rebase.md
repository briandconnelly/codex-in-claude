# 001 — Rebase the skill onto MCP 2026-07-28 as the single normative baseline

Decided 2026-07-29.
Plan developed with a Codex cross-check (disagreements verified against repo and spec text before adoption).

## Question

MCP 2026-07-28 finalized on 2026-07-28 and changes contracts this skill states normatively: statelessness, MRTR, the tasks extension, subscriptions, cacheable lists, and error-code renumbering.
The skill was written against 2025-11-25.
What baseline does the skill teach, and how does 2025-11-25 knowledge survive?

## Positions

*Dual baseline.* Teach both revisions side by side, since clients will speak 2025-11-25 for months.
Rejected: every capability rule becomes conditional, and each rule effectively gains a second home per revision — the drift mode `decisions/004` exists to prevent.

*Single 2026-07-28 baseline with informative compat.* Adopted.
The checklist binds against 2026-07-28 only.
Compatibility with 2025-11-25 clients is stated as explicit, version-bound interop outcomes in the owning rule (old clients can fail before tool invocation: they send `initialize`, expect session headers, call `resources/subscribe`, use core task augmentation, expect server-initiated `elicitation/create`; version mismatch is `UnsupportedProtocolVersion`, -32022).
`references/mcp-2025-11-25-compat.md` is **informative only**: version/feature matrix, old wire shapes, failure modes, pointers to governing rule ids — never prescriptive text.

## Subsidiary decisions

- **Rule-id retirement.** An id is preserved whenever its concern survives a mechanism change: `[7.task-support]` is rewritten around extension gating (`io.modelcontextprotocol/tasks` declared in per-request `clientCapabilities.extensions`; servers MUST NOT return task handles to undeclared clients), not deleted, because the concern — capability gating for tasks — survives the death of `execution.taskSupport`.
  An id is deleted only when its concern is gone; deletions are recorded in an informative retired-id table in the compat reference, since `tests/check_rule_ids.py` verifies only internal citations.
- **Atomic rebase.** One PR, three commits: this record plus the impact matrix; the semantic rebase touching every agent-consumed surface together; eval artifacts.
  No merged intermediate state may have SKILL.md and the references disagreeing on baseline.
  `tests/runs/` artifacts are immutable historical evidence and keep their 2025 baseline labels.

## Verified fact sheet

Checked 2026-07-29 against final spec text (`modelcontextprotocol.io/specification/2026-07-28/*.md` endpoints, `docs/extensions/tasks`, and `github.com/modelcontextprotocol/ext-tasks` `specification/draft/tasks.md`).
Re-verify wire spellings from these sources during the rewrite; do not trust this summary for exact JSON.

Two entries below were corrected in place on 2026-07-30, re-checked against the same sources.
The **Error codes** entry recorded `-32000..-32019` as "legacy/implementation-defined" in the first draft, which reads as available for new allocation; the band is legacy and closed, and the first draft also omitted the SHOULD that puts new application codes outside `-32768..-32000`.
The **Caching** entry omitted `server/discover` from the methods that MUST carry cache hints; issue #120's bullet inherited that omission, while `[8.cacheable-results]` had it right.

- **Per-request metadata** (basic/index § `_meta`): every request MUST carry `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in `_meta`; missing → `-32602` + HTTP 400. `clientInfo` is SHOULD; servers SHOULD return `serverInfo` in result `_meta`; both are self-reported, display/debug only, never security inputs.
- **resultType** (basic/index §Responses): required on every result; core values `"complete"` and `"input_required"`; extensions may add values (tasks adds `"task"`); unrecognized values are invalid; absent (older servers) MUST be read as `"complete"`.
- **Error codes** (basic/index §Error Codes): `-32000..-32019` legacy and closed — new codes MUST NOT be allocated there and new implementations SHOULD NOT use it at all; `-32020..-32099` spec-reserved; codes for purposes the spec does not define SHOULD go outside the JSON-RPC reserved range (`-32768..-32000`); assigned: `-32020` HeaderMismatch, `-32021` MissingRequiredClientCapability (carries `data.requiredCapabilities`), `-32022` UnsupportedProtocolVersion. Removed: `-32002` (folded into `-32602`; clients SHOULD still accept it from older servers) and `-32042` URLElicitationRequiredError (2025-11-25 only).
  Discrepancy to watch: the ext-tasks draft still cites `-32003` for the missing-capability error; core renumbered it to `-32021`. Cite the symbolic name plus core's number.
- **MRTR** (basic/patterns/mrtr): servers MUST use MRTR for `roots/list`, `sampling/createMessage`, `elicitation/create`; server-initiated requests are gone (breaking). `InputRequiredResult` is permitted only on `prompts/get`, `resources/read`, `tools/call`; MUST include at least one of `inputRequests` or `requestState`; `inputRequests` values are ElicitRequest | CreateMessageRequest | ListRootsRequest, and MUST NOT include modes/kinds the client did not declare. `requestState` is opaque, echoed verbatim on retry, and MUST be treated as attacker-controlled: integrity-protect (HMAC/AEAD) when it influences authorization or business logic, with replay protection SHOULD — this is the skill's §3 two-mode handle rule appearing as native spec text. Retry uses a new JSON-RPC id. Servers MUST NOT assume the client will retry.
- **Elicitation** (client/elicitation): survives as a capability with per-request mode declaration (`elicitation: {form, url}`; empty object = form-only backcompat); delivery only via `InputRequiredResult.inputRequests`; form mode MUST NOT collect credentials; URL-mode correlation via `requestState` (`elicitationId` and `notifications/elicitation/complete` removed).
- **Tasks extension** (`io.modelcontextprotocol/tasks`, ext-tasks spec): three methods — `tasks/get`, `tasks/update`, `tasks/cancel` (`tasks/result` and `tasks/list` removed). `CreateTaskResult = Result & Task` with `resultType: "task"`; server-directed per request (client never signals preference; server MUST NOT return a task to a client that didn't declare the extension; if it cannot proceed without tasking, it returns the missing-capability error naming the extension). Task fields: `taskId`, `status` (`working|input_required|completed|failed|cancelled`), `statusMessage?`, `createdAt`, `lastUpdatedAt`, `ttlMs` (nullable = unlimited; MAY change), `pollIntervalMs?` (MAY change). Task MUST be durably created before `CreateTaskResult` is sent; MRTR exchanges SHOULD resolve synchronously before task creation. Terminal payloads inline on `tasks/get`: `completed` carries `result` — **including tool results with `isError: true`**; `failed` carries `error` and MUST NOT be used for non-JSON-RPC errors (this inverts the 2025-11-25 `[7.failed-task]` coupling). `input_required` carries `inputRequests`, answered via `tasks/update` `inputResponses` (`UpdateTaskResult` has `resultType: "complete"`). Cancel via `tasks/cancel`; `notifications/cancelled` MUST NOT be used for tasks. Over Streamable HTTP, `Mcp-Name` MUST be the `taskId` on task methods. `notifications/tasks` (full task state) rides `subscriptions/listen`. The `io.modelcontextprotocol/related-task` and `model-immediate-response` `_meta` keys no longer exist.
- **Subscriptions** (basic/patterns/subscriptions): one `subscriptions/listen` request with a `notifications` filter — `toolsListChanged`/`promptsListChanged`/`resourcesListChanged` booleans plus `resourceSubscriptions: [uri...]`; every notification carries `_meta.io.modelcontextprotocol/subscriptionId` = the listen request's JSON-RPC id; cancel via `notifications/cancelled` on that id. Request-scoped notifications (`notifications/progress`, `notifications/message`) stay on the originating request's response stream.
- **Caching** (server/utilities/caching): `ttlMs` (integer ≥ 0) and `cacheScope` (`"public"|"private"`) MUST appear on `resultType: "complete"` results of `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`; ttlMs 0 = immediately stale, absent treated as 0, not a polling trigger; MRTR interim results MUST NOT be cached; the pagination `cursor` is part of the cache key.
- **Statelessness** (basic/index §Statelessness): no `initialize`/`initialized`, no `Mcp-Session-Id`; servers MUST NOT rely on prior requests on the same connection; cross-call state is referenced by explicit identifiers passed as ordinary arguments (SEP-2567 — native endorsement of `[1.state-handles]`).
- **Transport** (SEP-2243): Streamable HTTP POSTs MUST carry `Mcp-Method` and `Mcp-Name`; `x-mcp-header` passes custom headers from tool parameters.
- **Schema loosening** (SEP-2106): `inputSchema`/`outputSchema` accept any JSON Schema 2020-12 keywords; `structuredContent` may be any JSON value (not only an object); `$ref` external resolution off by default; composition-keyword resource bounds.
- **Unchanged**: `completion/complete` (`values`/`total`/`hasMore`); tool annotations; prompts surface.
- **Deprecated** (12-month window): Roots, Sampling, Logging, HTTP+SSE transport, `includeContext` `"thisServer"`/`"allServers"`, Dynamic Client Registration (→ CIMD).
- **Removed**: `ping`, `logging/setLevel`, `notifications/roots/list_changed`, SSE resumability (`Last-Event-ID`; broken stream = re-issue with a new request id).
