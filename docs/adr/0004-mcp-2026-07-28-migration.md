# ADR 0004: Stay on MCP 2025-11-25 and record the 2026-07-28 migration plan

**Status:** Accepted (2026-07-28)

## Context

MCP 2026-07-28 finalized on 2026-07-28
([modelcontextprotocol.io/specification/2026-07-28/basic/versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).
This server's wire shapes are still written against `2025-11-25`
(`mcp.types.LATEST_PROTOCOL_VERSION` in the installed SDK), which the new revision's
terminology page calls a **legacy** protocol version — one that "establish[es] a session with an
`initialize` handshake" — as opposed to a **modern** version (2026-07-28 and later), which conveys
"version, identity, and capabilities as per-request metadata" and has no negotiation handshake at
all. That target is not always what a given session negotiates: the installed SDK's
`initialize` handler (`mcp/server/session.py::ServerSession._received_request`) echoes back the client's
requested `protocolVersion` unchanged whenever it is one of `SUPPORTED_PROTOCOL_VERSIONS`
(`["2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25"]`, `mcp/shared/version.py`), and falls
back to `LATEST_PROTOCOL_VERSION` only when the request names something unsupported — so a client
that asks for `2025-06-18` gets `2025-06-18` back, not `2025-11-25`.
The gap (from an agent-friendly-mcp audit): the targeted revision was derivable only from the wire
(the `initialize` response), never stated in the agent-visible capability payload, and no
migration plan for the deprecated features already in use was recorded anywhere. The only
2026-07-28 awareness in the repo was a stale code comment in `_roots_from_ctx` calling the spec an
"RC" — it has been Final since 2026-07-28.

Every normative claim below was checked against the official specification pages (cited inline)
and against the installed dependency stack (`fastmcp==3.4.5` on `mcp==1.28.1`), not copied from
the vendored `.agents/skills/agent-friendly-mcp/decisions/001-mcp-2026-07-28-rebase.md` fact
sheet, which states of itself that it is routing/history only. That verification found the fact
sheet's relevant claims (in their current, already self-corrected form) accurate against the
official pages; the citations below are the independent check, not a copy of its prose.

## Decision

**Stay on `2025-11-25` for now.** Declare it explicitly in the agent-visible surface
(`CapabilitiesResult.protocol_revision`, populated by `codex_capabilities()`), and record this
document as the migration plan for its two in-use deprecated pieces: the roots capability, and the
2025-11-25 revision itself.

### Why 2025-11-25, and why not "the spec guarantees it a support window"

The installed dependency stack does not implement any part of the 2026-07-28 wire model:
`mcp.types.LATEST_PROTOCOL_VERSION == "2025-11-25"`, and a source search of the installed
`mcp`/`fastmcp` packages for `2026-07-28`, `server/discover`, and `subscriptions/listen` returns
zero matches. FastMCP's `Server`/`LowLevelServer` still speak the legacy `initialize` handshake
exclusively. Moving this server to 2026-07-28 today would mean hand-rolling the entire modern
per-request contract (stateless dispatch, mandatory `_meta` fields, `server/discover`,
`subscriptions/listen`) underneath a framework that does not yet expose it — not a configuration
change.

That justification is **deployment compatibility, not a spec-granted grace period**. The
versioning page is explicit that dual-era support is a server's *choice*, not an obligation to
legacy clients: "A server that wishes to support both legacy clients … and modern clients … **MAY**
implement both behaviors." Nothing on that page promises a legacy revision stays supported by the
ecosystem, by tooling, or by the spec itself for any duration — the compatibility matrix describes
outcomes, not guarantees, and a `Legacy`-client-vs-`Modern`-server pairing simply **Fails**. The
only timed guarantee in the whole rebase is the **per-feature** deprecation window covered next,
and it is not about revision support at all.

### The two timelines, kept separate

1. **Revision currency has no stated support window.** 2025-11-25 is now one revision behind
   Current; nothing in the versioning page commits to it remaining implementable, interoperable,
   or accepted for any further period. This server tracks FastMCP's own 2026-07-28 support as the
   real trigger to move (see Consequences).
2. **Feature deprecation has a stated minimum window, and it is per-feature.** The
   [feature lifecycle policy](https://modelcontextprotocol.io/community/feature-lifecycle) requires
   every deprecation SEP to "Specify the **minimum deprecation window**: the number of months, at
   least twelve, that the feature must remain Deprecated before it is eligible for removal,"
   counted "from the release of the specification revision in which the feature is first marked
   Deprecated." Roots was marked Deprecated in 2026-07-28
   ([client/roots](https://modelcontextprotocol.io/specification/2026-07-28/client/roots), SEP-2577),
   so its floor is **2027-07-28 at the earliest** — a statement about *roots*, not about whether a
   2025-11-25 server keeps working.

## Verified facts

Checked against the cited official pages (not against the vendored fact sheet):

- **Roots**: "Deprecated: The Roots feature is deprecated as of protocol version `2026-07-28`
  (SEP-2577). Under the feature lifecycle policy, it remains in the specification for at least
  twelve months … New implementations **SHOULD NOT** adopt it; existing implementations **SHOULD**
  migrate to passing directories or files via tool parameters, resource URIs, or server
  configuration."
  ([client/roots](https://modelcontextprotocol.io/specification/2026-07-28/client/roots))
- **Statelessness / per-request `_meta`**: "Servers **MUST NOT** rely on prior requests over the
  same connection to establish context … Every request supplies this metadata in its `_meta`
  field," and per-request `io.modelcontextprotocol/protocolVersion` /
  `io.modelcontextprotocol/clientCapabilities` are **required**; a request missing either is
  rejected with `-32602`. There is no negotiation handshake at all: "Servers **MUST** implement
  `server/discover`. Clients **MAY** call it before sending any other requests … but are not
  required to: a client is free to invoke any RPC inline" — it is an optional client pre-flight,
  not a mandatory replacement step, unlike the `initialize` handshake it stands in for on the
  legacy side.
  ([basic/index](https://modelcontextprotocol.io/specification/2026-07-28/basic/index),
  [basic/versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning))
- **Caching (`ttlMs`/`cacheScope`)**: "Servers MUST include caching hints on results with
  `resultType: "complete"` returned by the following operations: `server/discover`, `tools/list`,
  `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`."
  ([server/utilities/caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching))
  Matches the vendored fact sheet's own (already self-corrected, per its 2026-07-30 postscript)
  six-method list exactly — verified rather than assumed.
- **Error renumbering**: "`-32002` — resource not found (2025-11-25 and earlier; replaced by
  `-32602`)," listed under "Implementations of this protocol version **MUST NOT** emit these
  codes." This matches the brief's "`-32002`→`-32602` renumbering" claim exactly.
  ([basic/index § Error Codes](https://modelcontextprotocol.io/specification/2026-07-28/basic/index))
- **Subscriptions**: "`subscriptions/listen` opens a long-lived notification stream from the
  server to the client … It replaces the former `resources/subscribe` RPC and the HTTP GET
  endpoint."
  ([basic/patterns/subscriptions](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions))
- **Dual-era support is optional, not guaranteed to clients**: "A server that wishes to support
  both legacy clients … and modern clients … **MAY** implement both behaviors" — the word is MAY,
  confirming the compatibility framing above.
  ([basic/versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning))

## Per-feature migration plan

### Roots (deprecated feature, earliest removal 2027-07-28)

Low-effort: this server already treats roots as an **advisory fallback**, not the primary
workspace-resolution mechanism. `workspace_root` (an explicit tool argument) is the durable,
first-choice path on every tool that resolves a working directory; `_roots_from_ctx` only supplies
a fallback when `workspace_root` is omitted, and its own docstring already documents that
`workspace_root` is "the durable path" (now updated to point here instead of calling the spec an
RC). No code change is required to comply with the SHOULD-migrate guidance — the migration this
server would make (tool-argument scoping) is already the primary path, matching the spec's own
example of an acceptable migration target ("passing directories or files via tool parameters").
Plan: keep the fallback as-is; drop it only when/if the underlying MCP SDK removes roots support,
which the feature-lifecycle policy places no earlier than 2027-07-28 for the spec itself, later
still for SDK removal (SDK removal timing is explicitly the SDK's own policy, not tied to the
spec's floor).

### The 2026-07-28 revision itself (once FastMCP supports it)

No work is scheduled yet — FastMCP does not expose any of this — but the shape of the eventual
migration, so it does not need re-deriving:

- **Stateless per-request `_meta` + `server/discover` replacing `initialize`.** This server is
  already close to stateless in practice (every tool call is a self-contained request; no
  session-scoped mutable state lives across calls), so the mechanical change is in the transport
  layer FastMCP owns, not in this server's tool logic. `server/discover` becomes the version-probe
  entry point in place of the `initialize` handshake this repo's tests currently pin (see below).
- **`ttlMs`/`cacheScope` on list/read results.** `tools/list`, `resources/list`,
  `resources/templates/list`, and `resources/read` all gain mandatory caching hints. This server's
  tool catalog and resource set are effectively static within a process lifetime (`public` scope,
  a long `ttlMs`), while `resources/read` responses that vary per call (none currently do) would
  need `private` or a short `ttlMs`.
- **`-32002`→`-32602` renumbering.** `resource_error_carrier`
  (`src/codex_in_claude/schemas.py`) documents this server's resource-read error path as using the
  MCP numeric `-32002` (not found); a 2026-07-28 migration moves that to `-32602` and updates the
  documented carrier accordingly.
- **`resources/subscribe`→`subscriptions/listen`.** This server does not implement resource
  subscriptions today, so this is a no-op unless subscription support is added later, in which case
  it targets `subscriptions/listen` from the start rather than the removed RPC.

Each bullet above is scoped to what the installed SDK will eventually need, not a commitment to
implement optional features (subscriptions) this server has no plan to add.

## Consequences

- `codex_capabilities()` now discloses `protocol_revision: "2025-11-25"` directly — the wire-shape
  TARGET, not the per-session negotiated value (see Context: the SDK echoes back an older
  supported request unchanged), so a client can learn what this server's shapes are written
  against without inspecting `initialize`, but still reads a given session's own
  `initialize.protocolVersion` for what was actually negotiated on that connection. Additive
  field: not breaking.
- The trigger to revisit this ADR is **FastMCP/the `mcp` SDK shipping 2026-07-28 support**, not a
  calendar date — re-run the same verification (installed-package grep + the official spec pages)
  when that happens.
- The `initialize` wire shape this ADR describes as "legacy" is pinned by
  `tests/test_manifest.py::test_build_manifest_captures_initialize_without_version`
  (`serverInfo`/`protocolVersion`/`capabilities` presence) and by
  `tests/test_server.py::test_initialize_does_not_advertise_prompts`,
  `tests/test_server.py::test_initialize_does_not_advertise_the_ui_extension`, and
  `tests/test_server.py::test_initialize_ui_extension_filter_preserves_other_extensions` (the
  negotiated `capabilities` object). Any of these moving is exactly the kind of change this ADR's
  eventual migration would make.
- The rest of #423's vendored-skill sweep is already done: #448 rebased
  `.agents/skills/agent-friendly-mcp` onto the final 2026-07-28 spec, and `tests/runs/` transcripts
  are immutable historical evidence by declared policy (they keep their 2025 baseline labels on
  purpose). This ADR and the `protocol_revision` field are the only piece of #423 that was still
  outstanding in this repository's own agent-visible surface.

## Postscript (2026-08-31): the revisit trigger has fired

The Consequences section named "FastMCP/the `mcp` SDK shipping 2026-07-28 support" as the trigger
to revisit this ADR. fastmcp 4.0.0 (on mcp 2.1.1) ships it, and #570 ported this server onto that
stack — the server now serves both eras (the SDK offers no server-side era restriction), while its
wire shapes, error numerics, and manifest capture remain written against `2025-11-25`, which
`protocol_revision` still declares. The test named above,
`test_initialize_ui_extension_filter_preserves_other_extensions`, became
`test_ui_extension_filter_preserves_other_extensions` in that port (mcp 2 strips `extensions` from
the legacy `initialize` response, so the preserved-extension guard now asserts on the modern era).
The revisit itself — the per-feature migration this document records, the `-32002` -> `-32602`
renumbering the modern era mandates, cache hints, the discover-era manifest, and moving
`protocol_revision` — is tracked as #571. This document stays Accepted as the record of the
2026-07-28 *decision to wait*; #571's outcome supersedes or amends it.
